# 能力目录(两阶段选型)实验 —— 诚实的负结果(2026-08-22)

用户点的方向 4:两阶段选型降本,建"能力目录"加速查找。我建了 lexical 倒排 +
set-level 粗筛器(先例:retrieve→rerank,"Tools Are Not Islands" 的 set-level 检索;
选 lexical 不选 embedding 因为 230 规模够小、tags 是强信号、确定性可测)。

## A/B 实测(同一 HR 全家桶需求,满档)

| | 候选数 | 选型时间 |
|---|---|---|
| 粗筛开(DSH_ASSEMBLER_SHORTLIST=1) | 267→91 | 275s |
| 粗筛关(全量) | 267 | **174s** |

**粗筛开着反而更慢。** 这不是粗筛拖累,是**选型时间跟目录大小基本无关**——
275 vs 174 是满档推理的运行间抖动。选型慢的根因是**模型在满档下对架构使劲推理
(推理绑定)**,不是"读 267 条 vs 91 条"(输入绑定)——呼应几天前测的"一次装配
99% 墙钟是模型解码"。**压缩输入治不了满档推理时间。**

## 裁定

- 能力目录粗筛器**默认关**(DSH_ASSEMBLER_SHORTLIST=1 才开):它不提速、还有召回
  风险,不该误当提速上生产。
- 保留代码 + 单测:它是"训小模型做零件发现"的规则版基础(用户长期方向),
  以后可以用选型账本数据升级成学习版;也是"确定性预绑定明显匹配"这条真提速
  路径的基础(明显唯一匹配的需求跳过 LLM,只让它推理模糊的)。

## 真正的提速杠杆(从 930s 的 HR 账单看)

一次复杂装配 930s = 架构 spec 39 + 选型 275 + 探针推导 153 + 验收探针 162 +
**重试轮 297** + 前端验收 3。真正的时间黑洞:

1. **重试轮 297s** —— 首探 FAIL 触发的一整轮"重选型+重探针",是单笔最大浪费。
   降它靠**提高首探通过率**(更好的探针设计),而不是压选型输入。
2. **探针串行** —— 探针推导 153 + 多轮验收 162,可并行化。
3. **满档选型 ~170-275s** —— 推理绑定,只有降推理档能砍(用户裁定生产不降),
   或确定性预绑定明显匹配减少 LLM 要推理的需求数。

结论:方向 4"建目录加速"的直觉合理,但实测瓶颈不在查找、在推理。目录建成且正确,
但作为提速手段不成立;真提速要打重试轮和探针并行。诚实记录,不把负结果包装成正结果。
