# 真瓶颈打法 B:架构直构探针(2026-08-23)

## 背景

方向 4(能力目录)证明选型是**推理绑定**——压输入不提速。时间账摸清后,真瓶颈
= 满档推理两笔:选型 ~200s(用户裁定不降档)+ **探针推导 ~160s**。用户选定打法 B:
确定性构造探针,砍掉推导那笔。

## 设计:架构师顺手写探针草图,装配侧机械校验

不从 dataModel 字符串反解(脆),而是**让架构师在同一次 archSpec 调用里顺手把探针
草图写了**——它本来就在想 workflow,多写四个字段(createTask/retrieveTask/token/marks)
边际成本几秒,却把之后整段 ~160s 的探针推导 LLM 调用整个省掉。与 stateSchema 同款
"装配时预思考"原则。

装配侧 `validateArchProbe` 机械校验,每条闸都是战役真坑:
- 标记消毒(sanitizeMarks:代码碎片/过短剔除)
- token 自给自足(两轮指令都必须含 token:轮1 造它、轮2 按它取)
- **照抄闸**:取回轮不许把标记值复述在指令里(否则 agent 照抄指令即假 PASS——
  共享数据探针同款教训)
- 长度闸(自给自足的建档指令 <15 字符必是残缺)
任何一条不过 → null 回退 LLM 推导,不冒质量险。DSH_ASSEMBLER_ARCH_PROBE=0 强制全走 LLM。

archSpec 的探针指令浓缩了全部 MARK_RULES 血泪:空工作区自给自足、禁发明日期、
禁拒答话术、禁格式化数字、文件产出标记文件名、批量 ≤3 样本。

## 端到端实测(同需求双语读书助手,三次对照)

| | 总账 | 探针推导 | 重试轮 |
|---|---|---|---|
| 方向2初版(LLM 推导) | 333s | 161s | 无 |
| B 首跑(直构+假红) | 695s | **0s** | 302s(假红) |
| **B + 归一化匹配** | **265s** | **0s** | **无** |

B 首跑顺手揪出一个**匹配层类病**:标记「第2章第2段」被 agent 的「第 2 章 · 第 2 段」
判死——语义完全一致,排版变体让子串匹配假红,白烧 302s 重试。agent 干得完美,判卷器
把它判死了。类修:marksPresent 加**归一化双通道**(先精确子串;不中再剔空白/标点比对,
归一后 <2 字符不走归一防假阳)——治的是所有探针路径的标记脆性,不只架构直构。

终态:探针推导 0s(结构性省 ~160s)、首探一次全过、总账 265s(同需求最快)。
archSpec/选型仍有满档运行间方差(84s/133s),属推理绑定,不归本打法管。

13 项校验闸 + 4 项归一化匹配单测全绿;12 套件全绿。
