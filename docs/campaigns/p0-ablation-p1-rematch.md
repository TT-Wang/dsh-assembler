# P0 消融轮 + P1 复仇战战报(2026-08-24 凌晨)

## P0.4|BARE 消融轮(K)vs 现契约(H 基线)

`DSH_ASSEMBLER_BARE=1`(全部契约散文归零,只留代码闸与事实输出)× 8 场景,
对照 H 轮(同场景、同码、契约在场):

| | H(契约在场) | K(BARE) |
|---|---|---|
| 质量 | 8/8 PASS | 7/7 PASS(b04 尾场在跑) |
| 墙钟中位 | 161s | **343s(≈2×)** |
| 辅助思考 | 96.6k | **166.1k(+72%)** |

| 架构确认反问 | 每场有 | 几乎消失 |

**判读**:在 deepseek-v4 这一代上,契约散文是**承重的**——撤了它,match 滥用
立刻复发(硬预算句失效)、确认检查点消失、墙钟翻倍;质量靠考官兜住没掉。
Boris 的"删掉反而更聪明"在这一代此 harness 上**不成立**——但这正是消融仪式
存在的意义:**用数据裁定,不靠信仰;换模型代时重跑本轮,散文按到期制重审。**
(注:本轮为捆级消融;逐句消融待甲具支持。)

## P1 验收门|读书助手复仇战(app 形态 vs 模型中枢形态)

同一需求(上传 epub→分章入库→进度持久化→阅读页):

| | 模型中枢版(基线,账本在案) | 服务形态版(P1) |
|---|---|---|
| 上传通路 | 整本书 base64 塞进对话,由模型搬运 | 页面向 agent 要一次端点,字节直接 POST |
| 结果 | **物理性不可行**:2132 字符 base64 三轮手抄三坏,816s 求助判负 | 端点发现 4.8s → 直传落盘 **8ms** → 解析入库 12.8s |
| 全链路 | 40+ 分钟未通 | **18.0s,标记全中**(书名/章节题/正文句) |

装配本身:136s PASS,5 件精瘦(book-intake×2 + sqlite×2 + bilingual-reader),
缺口如实(翻译由模型产出、无零件);**自检包(selfcheck.json)首次实战落盘**。

过程发现两枚:
- 三岔口与缺口三选项契约实战生效:首轮 agent 把"造件/降级"摆成用户选项、
  被授权后正确走 index-add 流水线研究户型——卡在无头驱动批不了写仓库升权
  (真人可批;测试甲具的已知边界,非产品缺陷)。
- 它还如实指出 reader-upload-web-ui 模板仍是 base64 反模式——模板库待清扫。

**判读**:泛化 agent 裁定(模型不是强制中枢)的第一块试金石成立。app 型交付物
在服务形态下可装配、且碾压模型中枢形态;"vibe assembly 输给写代码"的读书助手
案例被撤销。
