## 判读

1. **F 速度与成本碾压**:Σ墙钟比 B 快 40%(HR 全家桶 80s vs 326s),辅助思考
   114.5k → 7.8k(仅剩考官偶发回退推导)。阶段 1 的 LLM 时间被结构性消灭;主
   agent 思考只多 14%——检索+决策被它顺手吸收了。**"零件专家的 LLM 映射"对这个
   规模(259 条)的目录不是必需品。**
2. **C 死于自己的判死线**:8/8 照抄草案,零红笔——"审阅"没发生,主 agent 思考也
   没省(111k vs B 102k),Σ墙钟最慢、辅助思考最贵。橡皮图章假设成立,C 出局。
3. **D 是死重**:8 场景(含模糊场)ask_catalog 零调用——模糊性在"用户想要什么"
   (agent 正确地反问了用户),不在"零件是什么"。自由问答对这个目录规模无人拉动,
   D ≡ B + 开销,出局(目录涨到数千条时可复议)。
4. **质量细看(parts.lock 地面真相)**:
   - F 的缺口报告**全场最诚实**:每条带落地方案("术语一致性由 SQLite glossary
     表实现"),还正确拒绝了 B 误选的 bilingual-reader 模板(场景不符)。词法漏检
     →假缺口的预判**未发生**。
   - F 的真病 = **过度选配**:催收 18 件(date×4/cron/节假日/电话/汇率全上)、
     HR 13 件含 3 个前端模板(只有第一个生效)。B/D 守住最小覆盖集(5-8 件)——
     match prompt 的"smallest covering set"规则是 B 仅存的独有价值。
   - 过度选配探针不惩罚(多装的零件不碍主流程),但运行时每个 mcp 行都是一个
     真进程 + 更宽的工具面 + 更多凭证面——是真实成本。

## 形态地图(本轮的交付物)

- 阶段 1 的最优解不是"谁的智力",是**检索(零 LLM)+ 最小集纪律**的组合:
  F 的速度 + B 的纪律。两条产品化路线:
  a) **hybrid 模式**:search_catalog 与 match_catalog 并存,教编排者"先检索,
     拿不准再请专家映射"——风险是 D 教训(可选工具可能永不被拉动/被滥用);
  b) **F + 纪律注入**(更简单,推荐):search 结果与 emit 契约里注入最小覆盖集
     规则;emit_preset 加机械超配提示(如 >10 件或 ≥2 个 frontend 时结果里点名
     让编排者复核)。
- C/D 形态归档不转产;draft_assembly/ask_catalog 代码保留 flag 后(负结果也是资产)。
