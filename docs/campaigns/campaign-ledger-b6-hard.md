## 共享数据探针四次加固(#1 的延续压测)

h08 供应链是比 f01 电商复杂得多的靶(14 张共享表),把共享探针的脆弱一层层压了出来:
1. **领域错配**:派生器让物流 agent 读采购单/对账 agent 读库存(共享表外)→ reader 找不到假红。
   修:prompt 铁律锁定 ONE 共享表 + table 字段校验。
2. **领域越界拒读**:reader 的 persona 不覆盖那张表,不肯查 → 修:readerTask 改成领域中立的
   显式 DB 查询(所有 agent 都有指向共享库的 sql 工具)。
3. **过精数字标记**:标记 `1000.00`,库存整数 `1000`,reader 报 "1000" 匹配不上(库检查证实数据
   其实写进去了)→ 修:载荷 token 改用 writer 额外写入的**独特字符串**(reader 任务里看不到,
   照抄骗不过),标记只用它。
4. **写入方漏写载荷**:writer 用领域语言建单,没把载荷字段写进去(NOT NULL/自然流程)→ 修:
   两端都改**显式 DB 操作**(探针职责是验共享库管道连通,不是验领域;领域已由各 agent 场景探针
   验过),并把完整 DDL 喂给派生器好填齐 NOT NULL 列。

四跑 PASS 实锤:purchase-agent 写 SKU-PROBE-7781 → warehouse-agent 从同一共享库读到。
**共享探针现在在简单(f01)与复杂(h08)方案上都稳定成立。**

关键教训:跨两个 LLM agent 的写→读探针,最大的坑是"两端都非确定"——reader 读错范围、
标记过精、writer 漏写。根治 = 探针回归到它真正的职责(管道连通性),用显式 DB 操作 + 独特
载荷 token + DDL 感知,把领域语言噪音全部隔离掉。
