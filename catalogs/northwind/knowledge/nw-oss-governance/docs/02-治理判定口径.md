# 治理判定口径(Northwind)

> **这份文件是示例策略,不是 Northwind 的真实内部规定。** 它的作用是给交付出来的
> agent 一份形状正确、逐条可检的判定口径,以便验收流程能跑通。真实交付时必须由
> 客户的合规与安全负责人用他们自己的规定替换本文件,并重新跑一遍知识门与探针。
> 上一份文件(两个上游的字段口径)里的每一条都是实测事实,与本文件性质不同。

## 一、严重度 → 处置时限

判定按下面的顺序取第一个能取到的值:定性标签 → CVSS 基础分 → 无severity则按"待评估"处理。

| 等级 | 判定依据 | 处置时限 | 是否可带病发布 |
|---|---|---|---|
| CRITICAL | 定性标签 CRITICAL,或 CVSS ≥ 9.0 | 24 小时内出整改方案 | 禁止 |
| HIGH | 定性标签 HIGH,或 CVSS 7.0–8.9 | 5 个工作日内修复 | 需 waiver |
| MODERATE | 定性标签 MODERATE,或 CVSS 4.0–6.9 | 下一个发布窗口 | 允许 |
| LOW | 定性标签 LOW,或 CVSS < 4.0 | 季度批量处理 | 允许 |
| 待评估 | 两种严重度都缺失 | 5 个工作日内人工定级 | 需 waiver |

**"待评估"不等于低危。** 缺少严重度字段只说明上游没给,不说明风险低。

## 二、许可证清单

| 分类 | 许可证 | 处置 |
|---|---|---|
| 直接放行 | MIT、BSD-2-Clause、BSD-3-Clause、Apache-2.0、ISC、Unlicense、CC0-1.0 | 无需审批 |
| 需要审批 | MPL-2.0、LGPL-2.1、LGPL-3.0、EPL-2.0 | 提交法务审批,记录用途与链接方式 |
| 禁止引入 | GPL-2.0、GPL-3.0、AGPL-3.0、SSPL-1.0、BUSL-1.1、Commons Clause | 禁止,必须替换 |
| 未知 | 字段为空、写作 UNKNOWN、或与仓库 LICENSE 文件不一致 | 按"禁止引入"对待,直到人工确认 |

**空的许可证字段按禁止处理**,不按放行处理——这是刻意的保守方向。

## 三、无可用修复时怎么办

命中漏洞但上游没有 `fixed` 版本(只有 `last_affected`,或干脆没有区间信息)时,按这个顺序找出路,并把选到哪一步写进报告:

1. 换掉这个包(优先,记录替代包与迁移成本)
2. 上游有未发布的修复提交 → 记录 commit,评估自行打补丁
3. 隔离使用面:确认受影响的代码路径在本系统里是否真的可达;不可达的记为"不可达豁免"并附证据
4. 都不成立 → 提 waiver,写明补偿控制措施与复查日期

**"等上游修"不是一个选项**,除非同时给出复查日期。

## 四、waiver 需要什么证据

一条 waiver 至少包含:漏洞 id、受影响的包与版本、为什么当期不修、补偿控制措施、复查日期、批准人。缺任一项的 waiver 不成立,agent 应当拒绝生成而不是补全空缺。

## 五、报告必须留下的东西

每份治理报告都要能被第三方复核,所以必须包含:

- 每条结论的**出处**:漏洞 id 与查询到它的上游
- 扫描时间(数据是活的,昨天的结论今天可能不同)
- 扫了哪些包、哪些包零命中(零命中也要出现在报告里,否则读者无法区分"没问题"和"没扫到")
- 数据署名:漏洞数据来自 OSV.dev,包元数据来自 deps.dev
- 一句明确的边界声明:许可证字段是注册表镜像,是参考信息不是法律结论

## 六、agent 不做的事

- 不替人做合规判定,只给出材料与按上表得出的分级
- 不修改任何仓库、不提交 PR、不改依赖文件
- 不在报告里写"安全"或"合规"这样的结论词,写的是"按本口径属于哪一级、需要什么处置"
- 严重度缺失时不猜一个分数填上
